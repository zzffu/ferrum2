# Unified runtime resolution and task-lifetime design — 2026-09-05

Design baseline: full-audit commit fc6180b2 and docs/architecture/engineering-audit-2026-09-05/runtime-dns.md findings RD-01/04/05/06/07. This is an implementation design, not new validation. The parent design records final integration decisions and takes precedence over unselected alternatives here. Read current runtime/DNS/RuleSet/net and client/server AGENTS, concrete query tracking/command loop, system lookup paths, generation socket/service, Direct UDP and reservation code. Applied codebase-design vocabulary: a deep module hides admission, cancellation, completion and join behind one small interface. No tests, builds, network, profiler, or dynamic reproducer were executed. Product files are unchanged.

## Decision: one DNS-owned system-resolution module, injected through existing net traits

| Design | Dependency/ownership consequences | Decision |
|---|---|---|
| DNS owns concrete bounded OS resolver and unique join owner; runtime receives implementations of net::TcpResolver/UdpResolver | dns already depends on net; both binaries and ruleset already depend on dns; runtime remains core/net only. System lookup, candidate shaping and redacted errors have one implementation. Runtime convenience constructors must accept a resolver instead of creating one. | Select. Smallest coherent migration that closes every current lookup path. |
| runtime owns OS resolver work and DNS/RuleSet reuse it | DNS -> runtime or RuleSet -> runtime violates current guides. Moving a generic blocking owner to net introduces Tokio task/OS implementation there, also prohibited. Binary-side injection alone leaves public DNS system defaults and RuleSet defaults creating independent/unowned work unless their defaults are removed anyway. Separate DNS/runtime owners duplicate budgets and shutdown. | Reject as common resolver implementation. Runtime still owns its protocol-neutral socket monitors and Direct UDP tasks. |

No new crate and no generic cross-crate blocking executor are required. net retains contracts only; no resolver implementation, Tokio owner, policy, global singleton or shutdown service goes there. Do not add a reverse edge from DNS/RuleSet to runtime for OwnerRegistry. DNS exposes closed counts and a joined shutdown report; binary composition maps them into the existing shared telemetry/report owner.

### Chosen external interface (names provisional, behavior binding)

A private dns `system_resolution/` module reexporting only:

- `SystemResolution::start(limits) -> (SystemResolver, SystemResolverOwner)`; construction creates one process-wide logical owner, not one per TCP flow or per ApplicationResolver. Limits are validated, injected values, never process-global env reads.
- Cloneable `SystemResolver` supports a DNS-specific bounded address query with an absolute deadline, and adapters implementing existing net `TcpResolver`/`UdpResolver`. The net traits need not learn DNS errors or join methods. Their existing caller deadline still cancels the logical waiter; the handle owns actual work independently.
- Unique `SystemResolverOwner::shutdown(&mut self)` closes admission, requests cancellation of work that has not started, and retryably joins all actual work and the dispatcher. A cancelled shutdown await leaves joins in that owner; a subsequent await resumes. Successful report means no commands, native operations, result buffers or join handles remain.
- No `Default`, zero-sized system backend, system_default constructor, hidden owner in Drop, or public raw join handles. Last resolver-handle drop may request shutdown, but it cannot report joined success. The unique owner must remain in a composition-owned closed state until observed completion.

The same handle is injected into `ApplicationResolver::system(...)`, fixed-endpoint system resolution, both RuleSet system branches, and any runtime direct-domain adapter. Configured resolver mode retains exactly its configured backend and cannot fall back to this handle. Direct numeric addresses bypass OS lookup exactly as before.

### Actual blocking-work admission and lifetime

Implementation uses an owner dispatcher retaining a bounded set of `spawn_blocking` handles around a private synchronous `std::net::ToSocketAddrs` adapter (the actual OS call). Do not wrap `tokio::net::lookup_host` in another async task: that leaves its internal blocking join inaccessible. The private blocking adapter is a real seam: OS implementation and deterministic existing-style test implementation vary here.

1. Validate/copy the bounded host and port before submit. Fixed endpoint lookup uses an explicit address-only request (internally port zero); do not force it through TargetAddr's nonzero-port contract. Runtime TCP/UDP preserve original system ordering and first-16 consumption; application/fixed/RuleSet adapters preserve their existing per-family selection/dedup/strategy semantics.
2. One work-slot permit covers accepted-but-queued, started and finished-but-not-joined work. Acquire it before enqueue; the bounded command channel and task registry share that same cap. Hold the permit through **join observation**, not merely until the blocking closure returns. Otherwise a fast stream of completed-but-unreaped results can escape the handle/result bound.
3. The request future gets only a reply receiver plus cancellation signal. The dispatcher, not that future, receives/owns the actual JoinHandle. Publish handle registration synchronously in the dispatcher with no cancellable await between spawning and storing it. The work closure retains its execution/input lifetime even if the request receiver is dropped.
4. Request deadline/receiver drop closes only the logical wait and marks the operation abandoned. Work not yet started checks cancellation before calling the OS. If the OS call is already running, it retains its work slot; discard its result when the native call returns, then observe join before releasing the slot. There is no replacement admission merely because a caller timed out.
5. The dispatcher consumes ready joins continuously and on every admission/shutdown boundary; result storage has exact fixed candidate bounds. Errors are closed `Busy/Timeout/Shutdown/Resolution/WorkerFailed`, without host/peer/source-error or panic payload formatting. Mapping into net io errors is closed (`TimedOut`, `WouldBlock`, `Interrupted` or `Other` as deliberately chosen); existing connector/RuleSet/DNS categories remain the composition contract.
6. Close admission atomically before draining shutdown commands. Drain and join everything despite first failure; keep a sticky WorkerFailed/cleanup result. Never equate aborting a started spawn_blocking handle with interrupting getaddrinfo. A caller no longer receiving a result does not release native budget.

Use one validated `max_system_operations` construction value for the process. For the first implementation, derive it from the existing bounded DNS max-inflight plan rather than adding a second user schema or hardcoding an arbitrary 16-worker throttle; document that this budget is separate from tagged-query permits even when initialized to the same number. The final default/cap and fail-fast Busy behavior require later normal workload validation: no promise of unchanged saturation behavior or performance is made by this design. No extra unbounded queue of waiting tasks belongs inside the owner. Preserve numeric fast paths and avoid a channel round trip for them.

OS limitations: portable getaddrinfo/ToSocketAddrs has no safe forced cancellation. Native resolver result allocation and NSS/provider behavior occur inside the OS/library before bounded Rust candidate collection. Bounded call count is not a proof of a hard native-memory or latency bound. A stuck OS call means shutdown may remain pending, admission remains occupied, and successful zero-owner evidence is unavailable. Ordinary grace expiry may report pending cleanup while retaining the unique owner, but must not destroy/recreate the owner or detach the join and claim success. A hard process-exit SLA would require a separately reviewed killable helper-process resolver or platform cancellation implementation, which is not selected here. No Windows DNS/route/adapter state change is required.

### Process bootstrap, normal run and materialize-only ownership

Construct the owner after offline validation, before the first endpoint or RuleSet materialization. A named closed `SystemResolutionState` in binary run/materialization ownership holds handle+unique owner together. Transfer that state once into run parts on successful materialization. For `--check-config --materialize`, join it after all temporary tagged/download users finish; preserve client failure exit 1 and server failure exit 2. Plain `--check-config` never constructs it.

Stop roots/admission first; cancel and join query, detour, Direct UDP and RuleSet users; then close/join system resolution; then report complete shutdown. On partial startup failure, close temporary users before joining the shared system owner. No generic forced-abort path may discard the unique system join owner. A generation reset may abandon generation-specific lookup waiters and forbid stale result publication, but the process-wide system work budget survives across reset; replacing the owner per reset would permit unbounded generations of abandoned native calls.

## RD-01: command-loop-owned query records, not cleanup after an untrusted body await

Current TaskSet has shared JoinSet ownership; registrar clones can keep the task set alive after the outer query unwinds. Move lifetime authority to a private DNS `query_owner` module with this interface: accept one command/context, run body, collect a closed terminal, close registrations, cancel/join descendants, deliver reply, then release admission.

Choose parent-retained `QueryRecord` over only wrapping the body in catch_unwind. The command loop retains for each bounded query: aggregate DnsQueryContext/admission, task-set owner, reply sender (closed enum for Lookup/LookupIps/Query), deadline/cancellation and task ID. The child body holds a weak registrar/query scope and produces a closed `QueryBodyResult`; the parent uses `join_next_with_id`/JoinError identity to find its record. Panic/abort before first poll still leaves the parent record and permit intact. Do not move sole cleanup state into a future that may itself be aborted.

TaskSet becomes unique owner + cloneable weak registrar. Registrar contains no strong reference capable of making a task->registrar->JoinSet ownership cycle. Its registration operation validates the query is open; close registration before draining children, including late child spawn races. Preserve weak dependency-chain scope with explicit admission retained by the root record. An accepted nested query inherits the same aggregate permit; it must not acquire a second system/tagged logical permit that can self-deadlock the dependency chain.

Descendant joins are never discarded. On a descendant panic, record sticky closed TaskFailed and notify/cancel that query body; ordinary completion and expected cancellation have distinct categories. Parent cleanup drains every descendant and nested query owned by the root admission before releasing it. A failed user reply send is not a cleanup failure; a panic/failed descendant join is. Query reply is sent only after cleanup under the existing contract; a timed-out caller may have already left, in which case drop result after cleanup.

Shutdown closes the command receiver and registration, resolves queued commands with Shutdown, signals bodies, joins all bodies, then closes and joins all records regardless of errors. Admission/counter release is the last step per record. Replace the magic 256-yield cleanup proof with explicit joins plus final counter assertions; counts are evidence, not a substitute for join ownership. Existing runtime-thread owner remains retryably awaitable and must be retained outside any cancelled query/root task. The owner report must not return success after a contained panic even if counters reach zero.

A private catch_unwind at the body future may improve immediate failure classification, using existing futures-util, but it is not the sole owner mechanism and must not restore poisoned mutable state. Do not format caught panic payloads or install a temporary process-wide hook inside query execution. Once-per-process closed diagnostic policy, if needed, belongs to binary startup.

## RD-06: tracked generation monitors owned by NetworkSocketService lifetime

Keep active monitors: removing them and relying only on poll-time checks would fail to close idle sockets during reset. The smallest safe module is private runtime `network_socket/monitor_owner.rs`, with one cloneable registration handle used by NetworkSocketService and one unique retryable join owner retained in binary network run parts.

- Reserve a bounded monitor slot before committing a successful physical socket resource. No spawned task escapes registration; constructors accept the registrar and return a closed capacity/owner error if it is closed/full. In-flight connect remains protected by existing coordinator ownership.
- Preserve exact current synchronous close sequence. TCP: take/drop physical stream before dropping NetworkRuntimeOwner acknowledgement. UDP: remove outer resource ref; await completion/cancellation of outstanding operation-held Arcs so physical socket Drop precedes owner acknowledgement. A monitor completing is not proof an operation-held UDP Arc is gone.
- Socket Drop closes its physical owner as it currently does, signals monitor stop, and returns; it does not own/drop a JoinHandle. Monitor JoinSet lives in the unique owner. Registrar is weak/closed, preventing strong-cycle retention. Count admitted/unjoined monitors until their joins are observed (not only while their bodies poll).
- Reset barrier requires both physical-generation owner acknowledgements and joined completion of monitors admitted to the retired generation. Use an explicit generation fence/snapshot token captured after admission closes for that generation; do not wait forever for monitors of the newly published generation. Existing physical reset timeout remains authoritative; exceeding it means reset fails/cleanup remains pending, not successful zero residue.
- Process shutdown closes monitor admission, requests stop, closes physical resource owners through the existing coordinator, joins all monitors, then releases network module. Retryable `shutdown(&mut self)` retains pending handles across await cancellation. Add monitor count to existing OwnerRegistry/closed report schema only once and update all exact-field consumers together; no parallel telemetry family.

Keep monitor mechanics in runtime, not net or platform; platform binding remains exactly one already-resolved interface decision. Current per-poll locks/boxed cancellation remain unchanged initially. Hot-path redesign is deferred until profiles show a benefit.

## RD-05: Direct UDP task completion is data, not an observer callback

Make task terminal outcomes explicit: `DirectUdpTerminal::{Completed,Idle,Cancelled,ResolveFailed,SendFailed,ReceiveFailed,HandlerFailed,Panicked,Aborted}` (collapse variants only if the current closed telemetry contract needs it). Retain a bounded task-ID -> generation-handle record outside each future so abort before first poll can be attributed. `JoinSet<()>` becomes joined closed outcomes; every `try_join_next` and shutdown drain uses one reaper. A no-op `let _ = result` branch is removed.

The current DirectOwnerLifetime guard remains responsible for exact-generation manager removal and physical resource/capacity rollback during unwind/abort. Move task-join permit/accounting to the parent task record so admitted-but-unjoined ownership remains charged until join. Socket ownership still releases when the socket is actually dropped. Reaping emits one returned completion record/aggregated closed counter, not a caller callback from task/Drop. The server loop selects on completions even when no new packets arrive; composition maps categories once into existing observability types. A slow consumer cannot create an unbounded event queue: return completions directly from the bounded task owner or accumulate fixed closed-category counts plus exact removal events already owned by the manager.

Normal Idle/Cancelled and a single target failure do not become process-fatal. Unexpected panic or invariant/cleanup failure is sticky in the shutdown report and visible to composition; do not pretend a reaped panic was a successful session. Replace shutdown's bare forced-count usize with a closed `DirectUdpShutdownReport` containing forced count and joined terminal summary/cleanup outcome. Retain graceful deadline lineage; abort remaining async tasks after forced deadline, then join all. Make shutdown retryable by borrowing the unique owner and retain it in the process cleanup state; dropping a consuming shutdown future must not discard nested task joins.

Keep R3/R6/R7 behavior: lifetime guard exact generation retirement, fair request/response scheduling, fixed buffers/backpressure, monotonic activity and no resurrected timer optimization. System resolver wait cancellation now returns to this owner without releasing actual native resolution budget.

## RD-07: reject generic transaction redesign; replace arbitrary closure exposure with concrete commit operations and containment

Rust has no safe trait bound proving that arbitrary user code cannot panic or reenter a mutex. Renaming `FnOnce` to `NoPanicCommit` would not fix RD-07. Also, moving protocol_commit outside the manager lock without a new generation/queue claim breaks reserve-before-commit atomicity. The server guide explicitly forbids replacing its concrete protocol/runtime sequence with a generic transaction framework.

Select the minimal corrective sequence:

1. Preserve the current single serialized runtime/protocol commit critical section and its move-only packet token. Encapsulate the injected operation behind a narrowly documented runtime `UdpProtocolCommit` interface returning a closed result; binary commit.rs and client response.rs own concrete request/single-response/batch-response adapters which hold only protocol references/tokens. No runtime manager, socket, resolver, callback or telemetry reference is passed to their method. Raw arbitrary closure-taking public variants are removed in the same change, rather than retained as compatibility aliases. A private no-protocol marker implements the numeric/plain datagram path.
2. `catch_unwind(AssertUnwindSafe(|| operation.commit()))` executes **inside** the scope where the manager guard is held; catch the panic before unwinding across that guard. Drop the guard before rollback or any outward propagation. Map panic into a closed commit failure and retire the exact affected runtime generation. Do not emit panic payload. This prevents manager poisoning/double-panic for the documented panic path; arbitrary panic in payload Drop or allocation abort remains outside recoverable guarantees.
3. Require implementors: synchronous bounded execution; no await/I/O; no reentry into runtime manager; no diagnostic formatting; no partial accepted mutation on a returned error. Concrete adapters are reviewed under those obligations. The trait itself cannot mathematically guarantee no reentry; containment fixes unwind, not deadlock. Current production adapters call only shadowsocks commit methods, so the intended implementations can satisfy it without a new transaction engine.
4. Protocol panic can leave protocol-owned state poisoned or partially changed even if runtime lock is intact. Do not claim rollback of arbitrary protocol side effects. Mark the protocol instance/session unavailable via its closed owner policy; on the next attempt fail closed. Prevent successful queue publication for the failed operation. A broad poisoning recovery that continues arbitrary partially mutated protocol state is rejected.
5. Make reservation/lifetime Drop paths non-panicking for recoverable cleanup conditions: centralize exact-generation pending decrement/removal in an audited cleanup helper; record sticky invariant failure rather than `expect`-panic during unwind. This is not a license to clear a poisoned manager and resume normal traffic. If unexpected internal poison is observed, close admission and perform safe destructive retirement only.

Alternative if later requiring structural freedom from all callback/reentrancy risk: expose a concrete claimed per-session commit lease, mark that session in-flight under manager lock, release the lock, commit protocol, then finish a pre-reserved infallible enqueue while cancellation/removal is deferred through the lease. Reentrant operations must return a closed busy result, never wait for the lease held by the same thread. This changes manager state, cancellation linearization and queue/drop semantics substantially. It is not selected for the first remediation and must not be smuggled into a cosmetic interface change. Cross-module protocol/runtime state cannot become atomically transactional merely by moving a closure call.

## Implementation order and later acceptance (planned, not executed)

1. Add DNS system_resolution deep module and private OS/fake seam; prove bounded accepted/queued/running/unjoined slots and retryable join; then migrate every system lookup caller and remove implicit defaults in one reviewable integration concern.
2. Add query_owner and parent-retained records, weak registrars and sticky completion failures; migrate all three commands together.
3. Track socket monitors with unique join owner, reset generation fence and coordinated owner-report schema update; preserve physical close-before-ack.
4. Preserve DirectOwnerLifetime cleanup, add data-only terminal reaper and retryable shutdown/report; map closed outcomes once.
5. Replace exposed raw commit closures with concrete adapters plus in-lock unwind containment/non-panicking retirement; verify protocol fail-closed behavior without claiming arbitrary rollback.

Later tests should demonstrate request cancellation while actual worker remains charged; queued cancellation before OS call; maximum admission with no handle growth; shutdown await cancellation/resume; query body/descendant termination across all commands; monitor blocked-before-first-poll and reset/drop ordering; UDP normal/error/panic/abort exactly once and owner baseline; returned protocol error remains mutation-free and commit panic cannot poison manager then double-panic. These are proposed test contracts only: existing automatic-review restrictions still prohibit retrying earlier blocked dynamic operations in this design turn.

No performance guarantee follows from static design. Preserve completed workload, no fallback, buffer/queue bounds, route-once and deadline semantics. After implementation and required safe gates, compare unprofiled paired throughput/latency/CPU per successful work under the reviewed policy. Only after architecture no-regression acceptance collect quick CPU profiles through existing Qualification workloads. System-resolution storms/churn, query cleanup and reset-turnover need targeted performance observations, but not a separate benchmark product or relaxed regression threshold.

## Composition supplement: network snapshot and native change-wait join owners

Additional current paths read after composition review: client `src/run/tun/network_lifecycle.rs::capture_network_snapshot` (spawn_blocking at :256) and its native change wait (:221), server `src/run/network.rs::reset_server_network` (:272) and `wait_for_network_change` (:295). Initial captures in client run.rs and server prepare_server_network_runtime are synchronous; they do not detach a JoinHandle, although their blocking startup cost remains an OS limitation.

Choose a **network-specific capture owner**, not a public OwnedBlockingOperation/executor abstraction and not the DNS system-resolution owner. Snapshot capture shares the physical network module lifetime and generation semantics. Add private runtime `network_socket/snapshot_capture.rs` with a single retained in-flight slot; expose only an operation such as `NetworkSocketService::capture_snapshot(generation)` through the existing network module. Its input is the requested generation, its implementation calls the already-owned `NetworkInterfaceCatalog`, and its output is a validated immutable NetworkSnapshot. It never accepts a caller-provided arbitrary blocking closure. Catalog sharing can use an internal Arc or a Clone requirement on this method, without putting an implementation in net or exporting another framework.

The unique network join owner designed for socket monitors also owns this capture slot and its shutdown state. An operation waiter does not own the JoinHandle: cancellation leaves the slot occupied and handle retained. Only joined completion clears the slot. Coalesce subsequent change notifications to a pending dirty/reason state rather than launching parallel replacement captures. No second capture is admitted until the first actual call has completed and been joined, even if a reset/phase waiter times out. The already-existing coordinator selects/publishes generation and rechecks it after capture; a stale result is discarded, never silently used for a newer generation. Keep route-change reasons even when interface snapshots compare equal; a snapshot omits concrete route contents.

This limits capture work to one native call per physical network module, with no unbounded queued requests. Shutdown closes capture admission, waits for that in-flight join, then joins monitors and returns a closed cleanup report. Generation retirement can abandon its capture consumer, but process-wide network work ownership survives; a new reset cannot create a second hidden blocking operation. GetIfTable/GetIpForwardTable behavior cannot be forcibly interrupted by aborting spawn_blocking; if the native call stalls, cleanup remains pending rather than reporting complete.

Keep native WindowsNetworkChangeMonitor ownership in the existing binary NetworkRoot/TUN network_lifecycle owner because platform-specific monitor types and stop/close operations do not belong in protocol-neutral runtime. Replace local `let mut waiting = spawn_blocking(...)` lifetime with a named private `NetworkChangeWaitState::{Idle(monitor),Waiting { join, stop },Closed}` retained by that root's external cleanup state. Normal cancellation already signals stop then awaits the handle; the missing case is cancellation/abort of the entire waiter future. Store the join before awaiting; on retry/shutdown recover the monitor from the joined result, explicitly close it and preserve errors. Stop-signal delivery/close remain platform adapters; no task abort stands in for native stop. Use one wait slot, no event-per-task spawning.

Concrete migrations: client `run/tun/network_lifecycle.rs`, its run/context lifecycle handoff and `run/egress/network.rs`/run.rs physical network owner construction; server `run/network.rs` preparation, reset, change-wait and rollback; runtime `network_socket/service.rs`, new private snapshot owner and monitor join owner, tests/network_socket_service.rs and owner/report field consumers. No new net, DNS, RuleSet or platform dependency edges. Preserve startup subscribe-before-initial-capture ordering. Planned tests cover cancelling capture await then retrying while one actual call remains, root shutdown while change-wait is in flight, capture failure preserving published generation, and all network-owned joins zero. None were executed in this design turn.
